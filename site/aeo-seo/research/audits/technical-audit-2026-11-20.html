1 · How search and AI search find you

Google

Crawlers read your pages, add the ones they trust to the index, then rank them for each search. Where you land depends on whether the page answers the search, and how much Google trusts the domain.

AI answer engines

ChatGPT, Perplexity, Claude and Google AI Overviews run their own searches on engines like Google, Bing and Brave, read the top results, and quote a few pages. If those engines can't find you, the AI can't either.

What this audit checks

That your pages are quotable (A), found fast (B), never contradict each other (C), and that the setup keeps itself right on every new page (D).

The structured data doesn't say clearly who's behind the site

Evidence

The homepage's JSON-LD parses and has WebSite, SoftwareSourceCode and FAQPage. King's Cross Labs only appears as a nested publisher with a name and URL: no standalone Organization, no logo, no sameAs links. The Person (Mika Reyes) has no sameAs either.

CriticalPartialB1Crawl files

The sitemap has no dates, so crawlers can't tell when the page changed

Evidence

/sitemap-index.xml → /sitemap-0.xml loads and lists https://content-creation-skills.com/ on the canonical host, but there's no <lastmod> (sweep: missing_lastmod 1). /sitemap.xml itself is a 404; robots.txt names the index, so crawlers still find it.

Where it lives

site/astro.config.mjs (the sitemap() integration has no serialize or lastmod)

The principle

The sitemap is the map you hand crawlers. An honest last-modified date tells them a page changed and is worth re-reading. Leave it out and they recrawl on their own schedule; set every date to the build time and they learn to ignore it.

Prompt to fix it
In site/astro.config.mjs, set lastmod on every sitemap entry from real edits, not the build time: at build, read the date of the last git commit that touched site/src (git log -1 --format=%cI -- src) and pass it through sitemap({ serialize }) as item.lastmod. Fall back to no lastmod if git isn't available. Verify: npm run build, then dist/sitemap-0.xml has a <lastmod> equal to the last commit date under site/src.
Effort: SOwner: your agent

ImportantPartialB2 · D1Crawl files

llms.txt is written by hand, and there's no full-text version for AI

Evidence

/llms.txt loads as text and opens with a one-line summary and the install command. It links the GitHub repo, the README and aeo-seo-skills.com, but not the skill list. It's a static file, so it drifts when site.ts changes. /llms-full.txt and /index.md are both 404.

Where it lives

site/public/llms.txt (hand-written)

The principle

llms.txt is a short, plain-text map of the site written for AI. It's only useful if it stays current. Generating it from the same data the page uses means it updates with every change, and a full-text version gives an AI engine the whole page without any HTML in the way.

Prompt to fix it
Replace site/public/llms.txt with an Astro endpoint, site/src/pages/llms.txt.ts, that builds the same file from src/data/site.ts: the summary, the install line, a line per skill with its status and GitHub link, and the FAQ questions. Add src/pages/llms-full.txt.ts (all page copy as Markdown, FAQs included) and src/pages/index.md.ts (a Markdown mirror of the homepage). Verify: npm run build, then dist/llms.txt, dist/llms-full.txt and dist/index.md exist and list every skill in site.ts.
Effort: MOwner: your agent
ImportantB5Crawl files

Nothing tells Bing when the site changes

Evidence

There's no IndexNow key file and no ping in the build, and the repo has no .github/ folder. The GitHub deployments API returns nothing for an environment named Production: Vercel names it Production – content-creation-skills, which matters when the workflow is written.

Where it lives

Nothing yet. It needs site/public/<key>.txt and .github/workflows/indexnow.yml

The principle

IndexNow tells Bing (and Yandex, Seznam and others) the moment a page changes, instead of waiting for a recrawl. Bing's index feeds ChatGPT search and Copilot, so on a site that's AI-first this is the fastest way to get changes in front of them. Google doesn't use it, which is why the sitemap still matters.

Prompt to fix it
Add IndexNow to content-creation-skills.com: generate a key, save it as site/public/<key>.txt, and add .github/workflows/indexnow.yml that runs on deployment_status when the state is success and the environment starts with 'Production' (Vercel names it 'Production – content-creation-skills', so don't match 'Production' exactly). It should POST every URL in https://content-creation-skills.com/sitemap-0.xml to https://api.indexnow.org/indexnow with the key. Never ping from preview deploys. Verify after merge: gh run list --workflow indexnow.yml shows a successful run, not skipped.
Effort: MOwner: your agent
ImportantPartialD2Checks

Nothing in the build checks titles, descriptions or the share image

Evidence

npm run build runs check-skills.mjs, which only checks that the skill list matches the skills/ folders. No check covers title length, description length, og:image or JSON-LD, which is how a 185-character description shipped.

Where it lives

site/scripts/, site/package.json

The principle

A fix that lives only in one sweep comes undone on the next edit. If the build fails when a description runs long or the share image goes missing, every future page is born right, whoever writes it.

Prompt to fix it
Add site/scripts/check-seo.mjs that reads every built HTML file in dist/ after astro build and fails the build if: the title is over 60 characters, the meta description is outside 110–160 characters or equals the title, there isn't exactly one H1, the canonical or og:url is missing or isn't on the canonical host, og:image is missing, or any JSON-LD block fails to parse. Run it at the end of npm run build and add npm run check:seo. List it in site/aeo-seo/site.md → Commands. Verify: npm run build passes on the fixed site, and fails if you lengthen the description.
Effort: SOwner: your agent

ImportantB10You

The site hasn't been submitted to Brave Search

Evidence

You confirmed on 2026-11-20 that the homepage hasn't been submitted.

The principle

Brave runs its own index, separate from Google and Bing, and AI tools that search the web through the Brave Search API read from it. A brand-new domain can sit outside that index for weeks unless someone hands it over.

Your steps
  1. Open search.brave.com/submit-url.
  2. Paste https://content-creation-skills.com/ and submit.
  3. Do the same for https://content-creation-skills.com/sitemap-index.xml.
  4. Done when the form confirms. A site:content-creation-skills.com search on Brave should show the page within a few weeks.
~2 minOwner: you

6 · Rules for new pages

The site is one page today, so these are for the first blog, comparison or use-case pages. Bake them into the page template and the check command (finding D2) so every new page is born with them.

  1. A real description. 110–160 characters, not the title (A1).
  2. A short title. Title plus the brand suffix, 60 characters or fewer (A1).
  3. Its own share image. 1200×630 og:image with twitter:card summary_large_image (A6).
  4. Answer first. The first sentence under the H1 and under each H2 answers it outright and names the subject (A7).
  5. 2–4 real FAQs on every guide or post, visible and in FAQPage markup (A3).
  6. In the sitemap with a true lastmod, and in the generated llms.txt (B1, B2).
  7. Linked both ways. Every new page links to the homepage and 2–3 related pages, and the homepage links back to it, so nothing is orphaned (B8).
  8. Byline and dates on articles: Mika Reyes, linked to a bio, with published and updated dates (A5).
